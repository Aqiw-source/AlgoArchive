配置编译器与运行用例

从找到 g++.exe，到亲手跑通第一组输入输出。

本章导航 找到真正用于编译的 g++.exe 在设置里保存并验证 用一组小数据验证整个流程 按现象排查 让 VS Code 与 AlgoArchive 使用同一个编译器 把一次错误保留下来做回归用例

找到真正用于编译的 g++.exe

已经用 VS Code 写 C++？可让 AlgoArchive 复用同一套 MinGW。打开 PowerShell，运行 where.exe g++ 查找 PATH 中的编译器；有多个结果时，用 VS Code 当前构建任务实际调用的那个路径。没有结果只表示 PATH 中没找到，并不代表电脑没有编译器；也可以从 VS Code 的构建任务中查看完整路径。

尚未安装编译器时，下载项目 v2.4.0 Release 页面上的独立 MinGW-w64 工具链压缩包（确认文件名为 MinGW-w64-GCC-8.1.0-Windows-x64-posix-seh-rt_v6-rev0.zip）。这是工具链附件，不是 AlgoArchive 源码包，也不是应用 ZIP 中附带的运行环境。

  1. 下载 ZIP 后先核对 SHA-256。PowerShell 示例（如果文件名或下载目录不同，请相应修改路径）：
    Set-Location "$env:USERPROFILE\Downloads"
(Get-FileHash -Algorithm SHA256 `
  .\MinGW-w64-GCC-8.1.0-Windows-x64-posix-seh-rt_v6-rev0.zip).Hash
    本附件已核验的摘要是 81a7de2010a66fa1a17b328bc9b8d7534596fe294d078d2cf4b6b706b083af97。忽略大小写比较应相同；摘要不一致时不要继续配置，请重新从 Release 下载。
  2. 先提取外层 ZIP，再用支持 7z 的解压工具，将 x86_64-8.1.0-release-posix-seh-rt_v6-rev0.7z 完整解压到固定位置，例如 D:\Tools。另一个 src-*.tar.7z 是源码，运行时不用解压。在二次解压后的目录找到 mingw64\bin\g++.exe；不要填写压缩包或目录，也不要只复制一个 exe。请保留 bin、lib、libexec 等配套目录。
  3. 在资源管理器地址栏点击 g++.exe 所在文件夹并复制路径，再在末尾加上 \g++.exe。例如最终路径形如 D:\Tools\mingw64\bin\g++.exe。实际提取目录可能不同，以你的机器为准。

在设置里保存并验证

  1. 在 Windows 本地版点左下角「设置」，再点「编译与运行」。也可使用这里的 前往编译器设置。若此页面通过 file:// 单独打开，请在完整程序目录运行 .\start.bat 启动本地版，再用服务地址打开手册并使用设置链接。
  2. 把完整的 …\mingw64\bin\g++.exe 文件路径粘贴到「g++ 可执行文件路径」。如需使用 PATH 中已安装的 g++，将输入框留空。初次配置建议先保留默认的 gnu++14。
  3. 点「保存编译器设置」。页面应显示实际路径和 g++ 版本；再点「编译能力检查」，等待 __int128、multiset 和 unordered_map 的真实编译运行检查完成。看到检查通过后，编译器配置和常用标准已就绪。
查找顺序、标准与时限

编译器查找顺序是：设置中填写的 g++ 路径优先；路径留空时，才从系统 PATH 查找 g++。如果填写了不存在的路径，程序会报告不可用，不会静默改用 PATH 里的另一套编译器。可选标准是 gnu++11、gnu++14、gnu++17、gnu++20、c++17 和 c++20；实际能否编译取决于所选 g++ 版本，默认是 gnu++14。

编译器单次编译有独立的 20 秒上限。编译成功后，每个测试用例另按「单例时限」运行，默认 3000 ms，可设为 50–30000 ms；运行全部时，这个时限分别用于每个用例，不能延长编译上限。Windows 下运行编译器和程序时，算法档案只为对应子进程把所选工具链的 bin 目录临时放到 PATH 前面，以便找到 MinGW DLL；不会改动系统或用户 PATH。

用一组小数据验证整个流程

打开左侧「代码试跑」并输入下面的程序。试跑草稿独立于题库，不必为了检查配置创建一道新题。

#include <iostream>
int main() {
    int a, b;
    std::cin >> a >> b;
    std::cout << a + b << '\n';
}
  1. 第一组输入填 2 3，期望输出填 5，运行当前用例。查看实际输出是否为 5。
  2. 再添加一组：输入 -2 2，期望输出 0，运行全部。两组均通过，就验证了编译、读入、运行和输出比较。
  3. 在正式题目的编辑页，点「保存用例」可供下次复测；已有的 CPH 用例可从 .prob 文件导入。

按现象排查

显示「未找到 C++ 编译器」
核对填的是 g++.exe 文件本身。优先填写绝对路径；如果刚修改过系统 PATH，请重启本地程序再检查。
能找到 g++，但编译提示缺少 cc1plus、库或 DLL
不要单独复制 g++.exe。重新完整解压工具链，保留 bin、lib、libexec 等目录的相对位置，再运行能力检查。
有多套 MinGW，版本对不上
以 AlgoArchive 设置页显示的实际路径和版本为准。VS Code 的任务、扩展或终端可能使用另一套编译器；核对两边各自调用的完整路径与 -std 标准，不要只比较系统 PATH。
保存时说路径无效
在资源管理器中重新复制实际路径，确认文件名以 g++.exe 结尾，并检查路径没有指向 ZIP 压缩包、快捷方式或源码目录。完整路径可以含空格或中文；随后点保存，确认页面报告检测到的版本。移动工具链目录后，请回到设置更新路径。
能力检查失败或报告编译错误
先展开检查结果并复制完整错误文字；回到编译设置，核对实际使用的路径、版本和标准。对自定义路径，打开 PowerShell 并运行 & "D:\Tools\mingw64\bin\g++.exe" --version（换成自己的路径）。若命令不能输出版本，重新解压完整工具链并改正路径。仍无法判断时，向支持者提供错误文字、应用版本、编译器完整路径及版本；不要发送题库、源码或个人数据目录。
能编译，但用例不通过
先读实际输出。如果题目只要一个数字，请去掉「请输入」之类的提示语，再检查换行、输入顺序和算法结果。
编译超时、用例超时、停止和运行错误有什么区别？
编译阶段超过 20 秒显示编译超时；编译通过后，每个用例另按「单例时限」判断运行超时；点击「停止」会主动终止当前任务；进程异常退出则显示运行错误。它们不是同一种失败。
本地用例通过是否等于 Accepted？
不是。本地结果只说明当前代码通过了你提供的测试用例；在线评测可能使用其他数据、编译环境和规则。请到对应 OJ 自行提交并查看结果。
自检通过，但试跑仍显示未找到 g++
自检.bat 会检查核心文件、运行环境和临时数据库；C++ 检查只报告是否找到编译器，不实际编译程序。没有 g++ 时自检仍可通过。配置后请另点设置中的「编译能力检查」，并用本章加法用例验证实际运行。
在在线演示里找不到本机编译器
GitHub Pages 演示是静态网页，只读写演示数据，不能调用你电脑上的 g++ 或设置系统功能。请下载 Windows 本地版执行本章步骤。

让 VS Code 与 AlgoArchive 使用同一个编译器

如果同一段程序在两处的表现不同，先在 AlgoArchive 设置里点「复制实际路径」。再看 VS Code 当前使用的构建任务或运行配置里调用的是哪个程序。若配置只写了 g++，在 VS Code 自带的 PowerShell 终端运行下面两行，比较命令实际指向的位置与版本。

(Get-Command g++).Source
g++ --version

已有绝对路径时，也可以单独验证它是否能够执行。以下是示例路径，请替换为自己的安装位置。PowerShell 中，路径两侧的引号和调用运算符 & 都有作用。

& "D:\Tools\mingw64\bin\g++.exe" --version

两端使用的 C++ 标准也要一致。确认编译器和标准后，再用上面的同一份加法代码、同一组输入分别运行，比较输出。

把一次错误保留下来做回归用例

保留加法程序的前两组数据，再做一次能识别错误的实验。临时把 a + b 改为 a - b，用输入 2 3 运行。实际输出应成为 -1，与期望的 5 不同。恢复加法并重新运行，结果应再次一致。

正式做题时，把触发问题的最小输入加到题目测试区，再保存用例。这样以后重构代码时，可以一键把原样例与反例一起运行。
